# V4: 隔离、审批与可执行验证

V3 仍直接修改主工作目录，完成状态由模型决定。V4 使用独立 Git worktree，并把验证加入状态图。

流程：Plan -> Baseline -> Act -> Tools -> Act -> Verify -> Repair 或 Finish。
只有明确传入的验证命令返回零且未超时，状态才是 verified；模型的完成消息只触发验证。
命令由用户通过 --verify 指定，默认在基线与最终验证时预授权执行。
模型请求的 run_command 使用 LangGraph interrupt，在数据库保存审批请求后才等待用户；拒绝作为工具观察返回。

```bash
forgecode --repo /path/to/repo --thread demo \
  --verify 'python3 -m unittest discover' '修复计算错误'
forgecode --repo /path/to/repo --thread demo --resume
```

新任务要求仓库已提交，避免静默漏掉未提交改动。修改保留在 `.forgecode/worktrees/demo`，
补丁导出到 `.forgecode/tasks/demo.patch`；不自动合并、不自动推送目标仓库。
检查后可使用 `git apply --check .forgecode/tasks/demo.patch`，再自行应用。

## 记忆与验证的边界

来源指纹变化、来源删除、超过 30 天或置信度过低的记忆不再返回。
验证成功的任务可保存 episodic 记录。置信度是启发式标签，不是概率校准结果。
worktree 只是文件工作区隔离，不限制网络、进程权限或共享 Git 元数据。
被批准的命令仍可能执行任意代码，测试本身也必须可信。
verified 只表示给定验证命令成功，不能证明测试充分，或模型没有通过篡改测试来取巧；
真实验收脚本另行检查测试文件未改动。

## 验证与已发现问题

17 个自动化测试通过，其中 V4 覆盖：

- 错误编辑 -> 实际 unittest 失败 -> 第二次编辑 -> 实际 unittest 成功。
- 审批 interrupt 后关闭数据库，再重新打开并批准执行。
- 主工作目录源码不变，导出补丁通过 git apply --check。
- 新文件、末尾空白、过期来源记忆和脏工作目录拒绝。

修复循环的工具执行与测试是真实的，模型决策采用固定序列以保证每次覆盖失败分支，不能当作真实 LLM 推理效果。
真实模型另由 `scripts/validate_reliable.py` 验证，凭据只从环境读取。
2026-09-21 真实验收通过：baseline_exit=1、final_exit=0、审批 1 次、工具调用 4 次、
total_tokens=9188；原工作目录未修改，导出补丁可应用。
开发中发现并修复：diff strip 丢失末尾空白；快速等长 Python 编辑可能复用字节码。
命令执行设置 PYTHONDONTWRITEBYTECODE，避免本流程产生旧缓存；既有外部缓存仍需用户管理。

崩溃恢复仍有副作用重放窗口，同一线程不支持并发执行。恢复时应使用与创建任务相同的功能开关。
