# V1 源码课：消息抽象、编辑与测试反馈

前置：[V0](V0.md)。后续：[V2](V2.md)。目标是独立解释“模型如何把一个 bug 修成真实 diff”。

## 1. 新增能力与未新增能力

V1 引入 LangChain 的消息、StructuredTool 和 ChatOpenAI 适配，但核心仍是显式 for 循环。
它新增 `edit_file`、`run_command`、`git_diff`，并在模型调用前裁剪上下文。
它没有 LangGraph、checkpoint 或强制验证；提示词要求测试，不代表程序一定保证模型先测试再完成。

## 2. 文件地图与继承

| 文件 | 关键对象 | 和 V0 的关系 |
|---|---|---|
| [v1/cli.py](../../v1/cli.py) | main、approve | 用终端确认回调装配工具 |
| [v1/agent.py](../../v1/agent.py) | SYSTEM、context、run | 保留循环，换成消息对象 |
| [v1/model.py](../../v1/model.py) | Model | 用 LangChain SDK 代替手写 SSE |
| [v1/tools.py](../../v1/tools.py) | Tools(ReadTools)、command | 继承 V0 路径和读取能力 |
| [tests/test_v1.py](../../tests/test_v1.py) | CodingTest | 真实编辑、真实 unittest、超时与裁剪 |

`class Tools(ReadTools)` 是继承。`super().__init__(root)` 先建立旧版 root/path 基础，之后安装新版工具列表。
`super().execute('read_file', ...)` 复用 V0 分派，而 `self.execute` 是 V1 的 StructuredTool 分派。
搞清 `self` 与 `super` 才不会误认为同名函数无限递归。

## 3. 新词汇

| 词 | 含义 |
|---|---|
| Pydantic | 根据模型声明校验输入数据并生成 schema |
| StructuredTool | 把函数、说明和参数 schema 组合成工具接口 |
| HumanMessage | 用户/外部输入消息对象 |
| AIMessage | 助手消息对象，含 content 和 tool_calls |
| ToolMessage | 执行结果对象，含 tool_call_id |
| subprocess | Python 启动外部进程的标准库 |
| argv | 可执行程序及其参数组成的列表，不是 shell 命令字符串 |
| exit code | 外部程序退出码，0 通常表示成功 |

TypedDict/普通类型注解与 Pydantic 不同：后者在工具调用入口实际验证字段，而前者主要描述类型。

## 4. 从模型接口读起

`Model.__init__` 构造 ChatOpenAI，指定 base_url、api_key、model、timeout、max_retries=1。
`complete` 有工具时 `bind_tools(tools)`；没有工具时直接调用 client，后续 V2 的 Plan 会复用这条路径。
`bind_tools` 只把工具声明传给模型，不会自动在本地执行任何函数。

`client.stream(messages)` 返回 chunk；用 `total + chunk` 合并正文、工具片段和 usage。
同时正文发事件给终端。结束后 `message_chunk_to_message(total)` 变成可存入历史的完整消息。
因此流式细节被 SDK 承担，但循环和执行时机仍然由自己的代码控制。
不用再手写 JSON tool call 解码，但应检查 `invalid_tool_calls`，V1 对这种协议错误直接终止。

## 5. 工具 schema 如何从函数得到

例如 `EditArgs` 的 path/old/new 定义了参数形状，Field.description 告诉模型字段语义。
`StructuredTool.from_function(self.edit_file, args_schema=EditArgs)` 将它绑定到实现。
函数 docstring 也成为模型可见工具描述，因此它不仅是给人的注释，随意改动可能影响模型选择工具。

执行路径：

```text
AIMessage.tool_calls
  -> tools.execute(name,args)
  -> 按名字找到 StructuredTool
  -> item.invoke(args)
  -> Pydantic 校验
  -> 调用 Python 函数
  -> 返回字符串观察
```

校验异常、I/O 异常等转为 error JSON；未知工具也返回 error。
StructuredTool 并不自动提供权限隔离，权限由 `run_command` 的 approve 回调承担。

## 6. 精确编辑逐步解析

`edit_file(path, old, new)` 首先调用继承的 path()，保证目标在允许目录中。
新文件只允许 old 为空；已有文件要求 old 非空并且 `text.count(old) == 1`。
例如文件中有两段 `return None`，模型只给这几个字符会被拒绝，需要带上更多上下文。

这是为了避免替换到错误位置，不是复杂的 diff/AST 编辑引擎。
它按全文字符串替换一次，new 最多 100000 字符，原文件最多 500 KB。
写入不是事务，也没有文件版本号/CAS 检查；并发修改仍可能产生竞争。
`old` 找不到时让模型重新读文件，比猜测“差不多”的位置更容易解释和测试。

## 7. 命令执行器逐段解析

审批回调默认拒绝。CLI 显示命令并要求用户输入 y，工具函数才调用 `command()`。
`command()` 本身是底层执行器，没有审批；后续 V4 的预授权验证也直接使用它。

```python
argv = ['python3', '-m', 'unittest', 'discover']
```

`Popen(argv, cwd=root, ...)` 没有 `shell=True`，所以 `&&`、重定向、通配符不会被 shell 自动解释。
但 `['python3','-c','任意Python代码']` 仍然可以执行任意代码，argv 不等于安全沙箱。

环境中名称包含 KEY/TOKEN/SECRET/PASSWORD 的变量会被过滤，降低传给子进程的直接凭据泄露。
这不阻止子进程读磁盘、网络或其它名称的凭据，不能把它描述成完整秘密隔离。
`PYTHONDONTWRITEBYTECODE=1` 防止本流程产生字节码缓存，不会删除已有旧缓存。

stdout/stderr 合并写临时文件，避免把全部输出长期存内存；返回最多 12000 字符。
临时文件的磁盘占用本身没有严格限额。30 秒超时后清理进程组，wait 回收进程。
`start_new_session=True` 便于向整个进程组发送信号，但主动脱离进程组的程序仍可能不受此清理覆盖。
这是 Linux/WSL 执行策略，不能宣称原生 Windows 直接兼容。

## 8. 上下文裁剪为什么按组

`context(messages, limit=60000)` 限制近似字符预算，不是精确 token 窗口管理。
前两条 system/user 保留；后续以 AI 消息开头分组，把一次工具请求及其观察保留在同一组。
从最近的组向前选择，超预算就停止。真实内部 messages 仍保留，裁剪的是发给模型的视图。

```text
保留：system, user, [AI工具请求 + Tool结果]
避免：system, user, Tool结果（没有对应请求）
```

局限：不是摘要，也没有长上下文知识压缩；若最新一组都太大，可连最新观察也不发送。
前两条特别长时也可能超过目标预算。面试要如实说它是启发式裁剪。

## 9. 完整执行示例

初始 `add(a,b)` 返回 `a-b`，测试期望 `add(2,3)==5`。

| 轮次 | 模型请求 | 环境返回 | 下一轮可用信息 |
|---|---|---|---|
| 1 | read_file | 错误实现 | 具体待改文本 |
| 2 | edit_file | edited 路径 | 修改已发生 |
| 3 | run_command | exit_code=0，测试结果 | 验证证据 |
| 4 | git_diff | `a-b` 变为 `a+b` | 真实变更范围 |
| 5 | 最终回答 | answered | 任务结束 |

这只是可能轨迹，不是 V1 强制状态机。模型也可能一开始就回答并退出，因此完成结果仍要独立验收。

## 10. 实验与预期

```bash
python -m unittest discover -s tests -p 'test_v1.py' -v
python scripts/validate_coding.py --windows-env
```

第一条不消耗模型 API；第二条调用真实模型，需要已配置的 Windows 变量。
测试中的 `Script.complete` 按固定序列产生 AIMessage，但文件编辑、子进程 unittest 都是真的。
真实脚本额外检查测试文件未被改动，并独立运行测试，不把模型说“成功”当作验收。

手动练习（仅在临时仓库）：

1. 放入两处相同 old，调用 edit_file，预期返回错误且内容不变。
2. 将 approve 换成永远 False，预期没有命令执行，观察含 denied。
3. 让命令 sleep 超过 timeout，预期 timed_out=True、非零退出码。
4. 在 test_context 中缩小 limit，观察是否还存在 AI/Tool 成对消息。

不要将这些练习直接作用于未备份的个人项目。

## 11. 面试问答

**为什么使用 LangChain 但不使用 Agent 工厂？** 复用协议、schema 和消息处理，保留自己的循环方便理解、测试与控制。

**精确替换与行号编辑相比有什么取舍？** 唯一文本匹配能发现内容漂移，但同段重复或格式变化时需重读；行号短但容易漂移。

**为什么命令需要审批？** 路径工具的约束不覆盖外部程序，批准 Python 等于允许其执行代码；先明确具体命令才能决定。

**你如何保证测试被执行？** V1 无法保证，只要求模型执行并检查真实轨迹；强制验证是 V4 解决的问题。

**为什么裁剪消息不是删掉最早 N 条？** 删除可能破坏工具调用配对；按组更能保持服务端协议合法性。

**运行测试通过就够了吗？** 不够，可能没发现测试、测试不足或被改写，需要验收器与人工 diff 审核。

## 12. 自测与下一版动机

你应能沿着一条 tool call 找到 StructuredTool、Pydantic 和实际 Python 实现。
应能解释 approval 与 command 是两层，不会误以为调用底层 command 自带审批。
应能指出当前进程崩溃会丢失消息历史，下一版才引入可恢复状态。
