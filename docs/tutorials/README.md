## 先补齐这些 Python 知识

| 语法 | 本项目里的用途 | 小例子 |
|---|---|---|
| 字典 dict | 消息、状态、工具参数 | `{"role": "user", "content": "hi"}` |
| 列表 list | 有顺序的对话历史 | `messages.append(answer)` |
| 函数与返回值 | 一个节点处理一份输入 | `def run(task): ...` |
| 类、self | 持有 root/config 等配置 | `tools = Tools(root)` |
| 继承、super | 新版复用旧版能力 | V3 Runtime 扩展 V2 Runtime |
| try/except/finally | 错误反馈与资源清理 | 网络失败也停止等待动画 |
| with | 保证文件/连接关闭 | `with sqlite3.connect(...)` |
| lambda/回调 | 传入审批、事件处理函数 | `lambda request: False` |
| yield | 逐个返回文件而非一次建大列表 | `Tools.files()` |
| 类型注解 | 描述输入形状；多数不做运行时校验 | `list[str]` |
| `python -m` | 以包路径运行模块 | `python -m v0.cli` |

不会某项时，可在独立草稿中写 5 行示例验证，再回到源码。不要在第一次阅读时把框架内部也全部展开。

## 通用阅读法

1. 找入口 `main()`，看用户输入被转换成什么。
2. 找核心函数 `run()` 或 `Runtime.build()`，画出下一步由谁决定。
3. 为每个对象写一句话：model 产出决策、tools 产生副作用、emit 发布事件。
4. 手算一个具体任务，记录每轮 messages/state 的变化。
5. 运行该版本测试，先读输入和断言，再读测试替身。
6. 做一个故障实验，例如拒绝命令、降低预算、制造歧义编辑。
7. 用自己的话写 150 字解释，标出“事实”“假设”“限制”。

## 为什么版本目录互相 import

每版保存新增机制，但不复制全部底层代码。比如 V4 继承 V3，V3 继承 V2，文件工具又复用 V1/V0。
最新源码是一个可运行系统，不是六套独立依赖环境。
历史完整状态保存在 Git 提交中：

| 版本里程碑 | 提交 |
|---|---|
| V0 | `d9c6e0e` |
| V1 | `c416f70` |
| V2 | `fe5fba4` |
| V3 | `9c5d723` |
| V4 | `2f49340` |
| V5 | `e24377d` |

可只读比较：`git show fe5fba4:v2/agent.py`。不需要切换当前工作区来学习。
后续公共工具有小修正，读当前 V0/V1 文件不一定逐字等于首发提交。

## 核心与界面的边界

| 模块 | 是否第一遍必读 |
|---|---|
| `vN/agent.py`、tools/model、repository/memory、oracle/evaluate | 是，逐版读 |
| `forgecode/config.py`、`trace.py` | 了解如何提供配置和事件 |
| `forgecode/ui.py`、`menus.py`、`history.py`、`interactive.py` | 可最后读，属于终端与用户体验 |
| `forgecode/session.py` | 最后读；它是多轮状态适配，包含审批逻辑，不是纯渲染 |

面试中不要把全部 `forgecode/` 都称为 UI：session 有运行时职责，config/trace 是基础设施。
区分层次的目的不是增加文件数量，而是让你替换终端显示时不用改模型循环。

## 面试证据分级

- 单元/集成测试通过：证明给定输入下运行机制符合断言。
- 固定模型序列 + 真文件/真测试：证明执行与修复分支，不证明 LLM 推理质量。
- 一次真实 API 任务成功：证明该配置的一次端到端可行性。
- 小样本消融：给出受限条件下的比较，不能自动推广到所有任务。
- 提示词承诺：只是对模型的指令，不是运行时强制约束。

建议面试展示一个真实 diff、一段工具失败观察、一条恢复记录和一张消融表。
不要把“像成熟编码助手一样有流式终端”当作核心技术贡献，也不要把单次成功包装成生产级可靠。
